# CPU and Vulkan flame rendering — 0.7.0

**Transform evaluation.** XML `coefs="a b c d e f"` maps a point to `(ax + cy + e, bx + dy + f)`. The pre-affine matrix acts first. If enabled, pre_blur displaces that point before the ordinary variation terms receive it. Signed term weights scale their contributions. The post-affine transform acts on the sum. The scalar color coordinate moves by `color_speed * (transform_color - old_color)`. Destination probability comes from its base weight times the previous transform's outgoing chaos multiplier. A missing multiplier equals one.

**Original registry.** The CPU implements FLAM3 IDs 0 through 14 in order: linear, sinusoidal, spherical, swirl, horseshoe, polar, handkerchief, heart, disc, spiral, hyperbolic, diamond, ex, julia and bent. Each accepts a variation weight. These historical IDs have no additional user parameters. Julia draws one branch bit from the Reborn sampler. Historical polar formulas in this range use atan2(x,y) where specified. The reference suite checks all 15, both Julia branches, signed weights and the affine conventions. Additional historical IDs and their parameter conventions appear in COMPATIBILITY.md.

**Plotting.** Each iteration advances the persistent orbit with an ordinary transform. A final transform, when present, acts on a plotting copy with the final transform's opacity as its application probability. For an untagged input, the ordinary transform sets sample visibility through the FLAM3 logarithmic opacity convention. A value of 0.5 contributes 0.1 of a full hit. The camera rotates around the flame center and projects using scale × 2^zoom. Increasing source Y goes down the output raster before rotation. Palette lookup uses the 256-entry coordinate convention, clamps at the last color, and supports step and linear sampling.

**Exposure.** The default sample budget is the ceiling of quality × width × height × 2^(2 × zoom), with a minimum of one. An explicit iteration budget overrides this. Each spatial bin accumulates source RGB and opacity with 24 fractional bits of effective precision (unit value 16,777,215). Per-bin logarithmic density accounts for camera scale and sample count. Spatial filtering combines the oversampled bins before the exposure passes through gamma and vibrancy controls. Background is composited before conversion to RGB8. The renderer reports requested samples, hits in frame and non-finite steps; repeated singular inputs can consume iterations without producing hits.

**Tagged Apophysis inputs in 0.3.0.** Recognized producer versions enable branch-specific transform conventions, nearest 255-scaled palette indices in step mode, quantized RGB buckets with a white level of 200, probabilistic ordinary-transform opacity and enabled final transforms. The Gaussian spatial kernel uses cutoff 1.8 and a truncated support diameter for tagged Apophysis inputs. FLAM3-style Gaussian inputs use cutoff 1.5 and retain the fractional diameter. Both support parity-correct subpixel placement and a histogram gutter. The gamma threshold blends the low-density response into regular gamma. Untagged inputs from 0.2.0 without an explicit radius retain box reconstruction. Historical integer-background compositing and vibrancy quantization are tested against original Pascal RGB results. See PRODUCER_ORACLE.md.

**Historical differences.** The ordinary CPU renderer uses mt19937_64 with a defined conversion to a 53-bit uniform number, batch-specific seeds and cumulative probability tables. The Vulkan path uses the separate portable stream described below. FLAM3 uses ISAAC and a quantized transform table. Other differences include density estimation, highlight handling, the precise sampling sequence and how non-finite orbits restart. FLAM3's adaptive density estimation, full historical filter family and animation timing are outstanding. The numeric and image reference reports identify which comparisons currently pass.

**Size and memory.** Preview rendering retains its dense subpixel histogram, costing 32 × width × height × oversample² bytes plus gutters and other buffers. File rendering now uses bounded sample chunks and reconstruction strips; it does not allocate the full histogram or image. A full 16,384² dense histogram alone would require 8 GiB at oversample one. The streaming file planner accounts for the model, metadata, sample buffers, row encoder and a strip with complete filter overlap. Host, GPU and disk budgets are checked separately. The host budget is for charged rendering buffers; Qt, runtime libraries, thread stacks and driver allocations can add to whole-process RSS. [Planning and actual 16K measurements](HIGH_RES_ACCEPTANCE.md)

**Output.** Streaming exports support RGB8 BMP, RGB8/16 PPM and RGB/RGBA8/16 PNG or TIFF. BMP uses top-down rows and a negative height; the earlier `write_image` API retains its positive-height bottom-up BMP representation. Both decode with the same orientation and RGB8 values. Sixteen-bit channels are quantized directly from double reconstruction, with no eight-bit intermediate. Straight alpha excludes the flame background; opaque RGB retains background compositing. An existing destination is replaced only after complete successful encoding. The [format contract](IMAGE_FORMATS.md) defines byte order, alpha and color semantics. JPEG/OpenEXR/ICC/dithering remain open output work.


**Editor preview.** The primary editor fits a model copy to its viewport and uses oversample one for interaction. It renders successive deterministic passes at increasing sample budgets. The largest pass replaces the earlier image. A stop token cancels obsolete jobs, including spatial reconstruction. The full-resolution file render uses the saved output dimensions and oversample value with a separately chosen sample and memory budget.

**Cancellation and progress.** Existing synchronous render callers retain their behavior. Optional cancellation throws `RenderCancelled`; optional progress reports completed requested samples after merged work batches. File output checks cancellation while encoding rows and before the staged file replaces its destination.

## Creative tools and variation coverage in 0.5.0

The registry now contains 31 variations. The ten additions are waves, fisheye, popcorn, exponential, power, cosine, rings, fan, eyefish and cylinder. They participate in the existing signed weighted sum between pre-affine and post-affine transforms. Waves, popcorn, rings and fan also use coefficients from that actual pre-affine matrix; final transforms supply their own coefficients. Producer-specific numerical guards and ring/fan formulas are retained. [VARIATIONS.md](VARIATIONS.md) records the complete registry and 640 independent original-source comparisons for these additions.

The Gradient and Adjustment editors preview working copies through the same CPU renderer. Palette hue/saturation/value changes, channel gamma curves and contrast alter the stored 256 RGB entries. Step/linear render interpolation controls how the orbit's color coordinate samples those entries. These palette operations remain separate from the flame's reconstruction gamma, gamma threshold, brightness, vibrancy and background. They do not add support for legacy non-default reconstruction curves. Transparent file export is provided separately by the 0.7.0 output layer.

Random generation and mutation also use this pipeline for candidate thumbnails and the selected preview. Each generated flame is a normal validated render model; accepted candidates or branches become collection entries. Generation estimates a camera from a deterministic finite-orbit sample. The Adjustment editor's explicit framing command uses the same robust estimate, covering the central 98% of sampled geometry with a margin and retaining the original camera if fitting fails. The fit applies the final transform to a plotting copy without feeding it back into the orbit. [CREATIVE_ALGORITHMS.md](CREATIVE_ALGORITHMS.md) defines the palette, generation, mutation and framing operations.

In 0.5.0 these tools used CPU sampling with oversampling-one interaction and separately configured file rendering. Version 0.6.0 adds the backend selection below while retaining those preview budgets and the original CPU path. Version 0.7.0 adds bounded file reconstruction, alpha output and separate full 16K acceptance without increasing interactive preview dimensions.

## Vulkan compute sampling in 0.6.0

The compute shader implements all 31 currently registered variations, including signed terms, affine-coupled formulas, per-transform pre-blur history and the admitted producer-specific branches. It performs weighted/Xaos selection, orbit evolution, final-transform plotting, camera projection, palette lookup, opacity and histogram accumulation. Each invocation owns a 256-sample chain plus 32 burn-in iterations. A PCG-style 32-bit stream produces 24-bit uniform draws; the full 64-bit seed and chain index determine each stream. This stream is deliberately separate from the established CPU sequence.

Orbit and palette calculations use FP32. Histogram R/G/B/opacity totals remain 64-bit integers, implemented through low/high 32-bit atomic words with carry. After completed compute work, the runtime reads the histogram back and uses the existing CPU reconstruction. Gaussian support, gamma threshold, brightness, vibrancy, producer background conventions and RGB8 output therefore remain in one shared implementation. The renderer reports sampling and reconstruction times separately.

The compute admission rules include at most 64 ordinary transforms plus one final transform, finite normal FP32 inputs, representable camera/addressing limits and selection intervals that survive both FP32 conversion and the stream's `2^-24` resolution. Special historical denominator restrictions are documented in [GPU_KERNEL.md](GPU_KERNEL.md). These checks do not guarantee that arbitrary nonlinear intermediate values remain finite. Invalid steps continue to be counted and recovered; chaotic trajectories and device math can still differ from double precision.

The CLI defaults to CPU; new saved desktop settings default to Automatic with CPU fallback. Automatic selection chooses usable physical Vulkan devices and excludes software devices unless explicitly selected. An unavailable loader/device, unsupported compute model or applicable GPU resource failure reports its reason and uses the CPU only when fallback is enabled. Strict Vulkan requests fail instead. Invalid input or inadequate host histogram/image storage remains an error. Cancellation never triggers fallback, and a failed or cancelled file render retains the existing destination.

`render_compute_reference` isolates numerical comparison by using the same portable streams and chain boundaries with the double CPU formulas. The executed integration fixtures and direct variation probes are recorded in [GPU_TESTING.md](GPU_TESTING.md) and [GPU_KERNEL.md](GPU_KERNEL.md). Execution here used llvmpipe software Vulkan; physical-GPU speed and Windows-driver behavior remain unverified. See [GPU_RENDERING.md](GPU_RENDERING.md) for controls and [WINDOWS_GPU.md](WINDOWS_GPU.md) for the strict platform check. CUDA is not implemented. Milestone 7 adds the bounded hit-stream variant for file rendering; it retains the compute chain identity and mathematical admission rules while avoiding a full GPU histogram allocation. See [GPU_STREAMING.md](GPU_STREAMING.md).

## File sampling, strips and restart in 0.7.0

CPU and Vulkan file sampling emit hits in the coordinates of the complete padded histogram. Chunks are written once and indexed by global row group. A reconstruction strip loads the groups covering its own rows and filter overlap, then evaluates the same camera, density, gamma and filter settings as the complete render. Strip height therefore changes memory and I/O behavior without changing the sampling stream or image. Exact dense/stream comparisons cover 30 CPU and six Vulkan configurations; a complete 16K comparison also matches every PNG byte with different strip heights and worker counts, including pause/resume. [Acceptance evidence](HIGH_RES_ACCEPTANCE.md)

The checkpoint manifest advances only after its complete chunk is flushed. Resume validates identity, counters, continuity and checksums before using sampled data. Committed CPU batches may resume with a different worker count. Committed Vulkan samples require the original device/driver/shader identity; fallback is only possible before the first committed GPU chunk. Cancellation during reconstruction retains sampling but restarts reconstruction from the first strip next time. A killed-process recovery check independently demonstrates a released process lock, a preserved prior destination and byte equality after resume in a new process. [Checkpoint operations](HIGH_RES_RENDERING.md)
